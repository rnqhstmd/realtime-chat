4. 요구사항
4.1 필수 구현
아래 항목은 실제로 동작하도록 구현해 주세요.
	•	실시간 기반 메시지 송수신
	•	사용자 join / leave 처리
	•	기본 presence 처리(online/offline 또는 세션 참여 상태)
	•	이벤트 또는 메시지 수집 API
	•	중복 이벤트 방지 또는 중복 반영 최소화를 위한 합리적 전략 반영
	•	순서 뒤바뀜 상황에 대한 일관된 처리 기준 정의 및 반영
	•	특정 시점 기준으로 세션 상태를 복원하는 API 또는 기능 1개
4.2 필수 설계/문서
아래 항목은 구현 또는 문서 중 하나로 제출 가능하며, 문서만 제출해도 됩니다.
DB 설계 제출물
	•	ERD 또는 테이블 관계를 설명하는 문서
	•	핵심 테이블 DDL 일부(예: Session, Participant, Event/Message, Snapshot/Projection)
	•	주요 조회를 위한 인덱스 설계 근거(핫패스 중심)
<aside>
정규화, 비정규화, JSONB 등 선택은 자유이나, 선택 근거와 트레이드오프를 명확히 기술해 주세요.
</aside>
REST API 설계 제출물
	•	세션 생성, 이벤트 수집/조회, 상태 복원 기능을 제공하기 위한 API 스펙(OpenAPI 권장)
	•	최소 API 예시는 아래와 같으며, 필요에 따라 조정할 수 있습니다.
	◦	POST /sessions (세션 생성)
	◦	POST /sessions/{id}/join (참여)
	◦	POST /sessions/{id}/events (이벤트/메시지 수집)
	◦	POST /sessions/{id}/end (종료)
	◦	GET /sessions (세션 목록 조회: 기간/상태/참여자 등 필터)
	◦	GET /sessions/{id}/timeline?at=... (특정 시점 상태 복원)
	◦	(선택) POST /sessions/{id}/snapshots (스냅샷 생성/갱신)
	◦	(선택) GET /sessions/{id}/events?from=...&to=... (디버깅/검증용)
설계 문서에 포함해 주세요
	•	재연결 시 데이터 정합성을 유지하는 방식
	•	서버 수평 확장 시 세션 분산 및 상태 저장 전략
	•	관측 가능성 설계(로그, 메트릭, 추적)
	•	비동기 처리 구조(Projection 업데이트, Snapshot 생성, 재시도, DLQ, Idempotency)
	•	장애 대응 시나리오
	◦	서버 다운(인스턴스 장애)
	◦	DB 장애 또는 성능 저하(커넥션 고갈, 락 경합 등)
	◦	데이터 유실 또는 정합성 이슈(중복 저장, 부분 실패 등)
4.3 이벤트 기반 상태 복원 기능
대화 중 발생한 모든 이벤트(Event)를 기반으로, 특정 시점의 대화 상태를 복원하는 기능을 설계 또는 구현합니다.
복원 대상 예시
	•	특정 시점 t 기준으로:
	◦	해당 세션에 존재하는 참여자 목록(입장/퇴장 이벤트 반영)
	◦	대화창에 보여야 하는 메시지 목록(또는 최근 N개)
	◦	각 메시지의 상태(전송/수정/삭제 이벤트가 있다면 반영)
	◦	(선택) unread count, typing indicator 등 추가 상태
필수로 설명해야 할 내용
	•	프로젝션 또는 리플레이 전략
	◦	전체 이벤트 리플레이로 복원할지
	◦	스냅샷 + 이벤트 리플레이 방식으로 복원할지
	•	중복 이벤트 및 순서 뒤바뀜을 복원 로직에서 어떻게 다룰지
	•	복원 비용과 성능을 고려한 설계(인덱스, 스냅샷 주기, 저장 포맷 등)
구현 시 가산점이 되는 내용
	•	Snapshot + Replay 기반 복원 최적화 구현
	•	Projection 비동기화 구현
	•	재연결 시 resume / replay 고도화
4.4 쿼리 최적화 및 트러블슈팅 시나리오
아래 내용을 문서로 제출합니다.
(1) 쿼리 / 인덱스 최적화
	•	대화 데이터가 대량으로 쌓일 때의 조회 성능 전략
	•	핫패스 기준으로 2~3개 주요 쿼리에 대해 아래를 포함
	◦	SQL
	◦	인덱스 설계
	◦	예상 병목 및 개선 방향(텍스트 설명)
(2) 비동기 처리 설계(해당되는 경우)
	•	Snapshot 생성 또는 Projection 업데이트를 비동기로 분리하는 경우의 구조
	•	재시도(지수 백오프), DLQ, Idempotency, 중복 실행 방지 설계
(3) 장애 대응 시나리오(운영 관점)
아래 3가지 상황 각각에 대해 감지 -> 완화 -> 복구 흐름으로 기술해 주세요.
	•	서버 다운(인스턴스 장애)
	•	DB 장애 또는 성능 저하(커넥션 고갈, 락 경합 등)
	•	데이터 유실 또는 정합성 이슈(중복 저장, 부분 실패 등)
