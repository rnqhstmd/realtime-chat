# realtime-chat

실시간 대화 세션의 메시지 송수신·presence를 처리하고, 모든 이벤트를 기록하여 특정 시점의 세션 상태를 복원하는 시스템.

## 배경

실시간 대화에서는 메시지 송수신, 참여자 입퇴장(join/leave), presence(online/offline) 같은 사건이 끊임없이 발생한다. 단순히 "현재 상태"만 저장하면 다음을 만족하기 어렵다.

- 재연결한 클라이언트에게 끊긴 시점 이후의 상태를 정확히 복원해 줄 수 없다.
- "특정 시점 t에 대화창이 어떤 모습이었는가"를 사후에 재구성할 수 없다.
- 네트워크 지연으로 이벤트가 중복 도착하거나 순서가 뒤바뀌어도 일관된 결과를 보장하기 어렵다.

이 시스템은 발생한 모든 사건을 **이벤트(Event)** 로 누적 저장(이벤트 소싱)하고, 이벤트 리플레이 또는 스냅샷+리플레이로 임의 시점의 상태를 복원한다.

## 안 하면 어떻게 되는가

상태만 저장하는 구조로 가면 다음 리스크가 누적된다.

- **재연결 정합성 깨짐**: 클라이언트가 잠깐 끊겼다 붙으면 그 사이 메시지/입퇴장을 정확히 따라잡지 못해 화면이 어긋난다.
- **감사/디버깅 불가**: "그 시점에 누가 있었고 무엇이 보였는가"를 증명·재현할 수 없다.
- **중복·순서 이슈 방치**: at-least-once 전달 환경에서 중복 저장·순서 뒤바뀜이 그대로 상태에 반영되어 데이터가 오염된다.

> 본 도메인은 과제 요구사항(`requirements/과제요구사항.md`) 기반으로, 위 리스크를 다루는 설계·구현이 평가 대상이다.

## 사용자와 규모

- **사용자**: 실시간 대화에 참여하는 클라이언트(앱/웹) 및 시스템을 검증·운영하는 평가자/개발자.
- **규모(전제)**: 과제/POC 수준. 동시 세션 수백~수천, 세션당 메시지 수천~수만 건 규모를 핫패스·인덱스 설계의 기준으로 삼는다.

## 성공 기준

- 실시간 송수신, join/leave, presence가 실제로 동작한다.
- 이벤트 수집 API가 중복 방지(Idempotency)와 순서 뒤바뀜에 대한 일관된 처리 기준을 갖는다.
- 특정 시점 `at` 기준으로 참여자 목록·메시지 목록·메시지 상태를 복원하는 기능/API가 동작한다(`GET /sessions/{id}/timeline?at=...`).
- DB 설계(ERD/DDL/인덱스 근거), REST API 스펙(OpenAPI), 비동기/관측성/장애 대응 설계 문서가 제출된다.
- 핫패스 쿼리 2~3개에 대한 SQL·인덱스·병목 분석이 문서화된다.

## 기술 스택 / 아키텍처

- **스택**: Spring Boot + PostgreSQL + Redis(단일 인프라 — Stream·Pub/Sub·presence)
- **아키텍처**: 이벤트 소싱 + CQRS (이벤트가 유일한 진실의 원천, 읽기 모델은 projection)
- 상세 설계와 모든 결정의 이유: [이벤트 소싱 기반 설계서](../../docs/design/2026-05-28-realtime-chat-design.md)
