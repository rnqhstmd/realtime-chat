# 요구사항 추적 매트릭스 (RTM) — 실시간 대화 세션

- 작성일: 2026-05-28
- 요구 출처: [`requirements/과제요구사항.md`](../../requirements/과제요구사항.md)
- 설계서: [`2026-05-28-realtime-chat-design.md`](./2026-05-28-realtime-chat-design.md) (이하 "설계서 §n"으로 참조)

> **목적**: 과제 요구사항 한 항목마다 "무엇을 원했나 → 왜 원했다고 해석했나 → 그래서 어떤 설계 결정을 했나 → 그 이유 → 설계서/코드 위치"를 1:1로 추적한다.
> **읽는 법**: `의도(왜)` 열은 요구 원문 너머의 평가 포인트를 해석한 것이다. 설계 결정은 그 의도를 충족하기 위한 선택이다.

## 4.1 필수 구현

| ID | 요구 (원문 요지) | 의도 (왜 원하나) | 설계 결정 | 이유 | 위치 |
|----|------------------|------------------|-----------|------|------|
| R-1 | 실시간 기반 메시지 송수신 | 폴링이 아닌 푸시형 양방향 통신을 구현할 수 있는가 | STOMP over WebSocket, inbound는 REST `/events`와 동일 command handler로 수렴 | 양방향엔 WebSocket이 적합, STOMP는 sub/pub·Spring 통합으로 보일러플레이트 절감. 수집 경로가 둘이어도 멱등·순서 로직을 1곳에 모아 일관성 | 설계서 §6, §11 |
| R-2 | 사용자 join / leave 처리 | 참여자 생애주기를 상태가 아닌 사건으로 다루는가 | PARTICIPANT_JOINED / LEFT 이벤트 → participant_view projection | 입퇴장도 불변 이벤트로 기록해야 "특정 시점의 참여자"를 복원 가능 | 설계서 §3.2, §4.3 |
| R-3 | 기본 presence 처리(online/offline) | 휘발성 고빈도 상태를 적절한 저장소로 분리하는가 | Redis TTL 키 + 하트비트, 변동은 PRESENCE_CHANGED 이벤트로 감사 기록 | presence는 휘발성·고빈도 → Redis TTL이 적합. 영속 감사 목적만 이벤트화 | 설계서 §6 |
| R-4 | 이벤트 또는 메시지 수집 API | 모든 사건을 단일 수집 관문으로 받는가 | `POST /sessions/{id}/events`, REST/WS 공통 command handler | 수집 진입점을 단일화해야 멱등·순서·검증을 일관 적용 | 설계서 §11 |
| R-5 | 중복 이벤트 방지/최소화 전략 | at-least-once 환경의 중복을 합리적으로 막는가 | 2계층 멱등성: ① `UNIQUE(session_id, idempotency_key)` ② projection `last_applied_seq` 가드 | 중복 *유입*과 중복 *적용*은 다른 실패 지점 → 두 계층 모두 필요 | 설계서 §4.1 |
| R-6 | 순서 뒤바뀜 일관 처리 기준 | 순서의 "기준"을 명확히 정의하는가 | 순서 권위 = 서버 append 시점의 세션별 seq. projection은 seq-guard로 재조정 | 분산에서 클라 순서는 신뢰 불가 → "서버 수신 순서 = 진실"을 명시적 계약화 | 설계서 §4.2 |
| R-7 | 특정 시점 세션 상태 복원 API 1개 | 임의 시점 t의 상태를 재구성할 수 있는가 | `GET /sessions/{id}/timeline?at=` — snapshot(≤at) + event replay(snapSeq, atSeq] | 이벤트 소싱의 핵심 산출. 스냅샷+부분 리플레이로 복원 비용 상한 고정 | 설계서 §4.3, §11 |

| R-11 | 정규화/비정규화/JSONB 선택 근거·트레이드오프 (aside) | 저장 포맷 선택을 트레이드오프로 정당화하는가 | 쓰기=JSONB, 읽기=정규화 테이블 (혼합) | 이벤트는 이질적이라 JSONB로 균일, 검증은 커맨드 경계에서. 읽기는 인덱스 효율 위해 정규화 | 설계서 §2.1(payload), §3, Q2-3 |
