## 0. 면접 진행 전략

### 30초 엘리베이터 피치 (먼저 이렇게 연다)

> "실시간 대화 세션을 **이벤트 소싱 + CQRS**로 설계했습니다. 핵심 통찰은 — 과제의 진짜 요구가 '특정 시점 상태 복원'인데, 이건 *현재 상태*가 아니라 *상태 변화의 이력*을 진실의 원천으로 두면 자연스럽게 풀린다는 점입니다. 모든 사건을 불변 이벤트로 append하고, 읽기 모델은 projection으로 파생하며, 시점 복원은 스냅샷+부분 리플레이로 합니다. 이렇게 하면 중복·순서·복원·감사·재구축이 **하나의 일관된 모델**에서 나옵니다."

### 화이트보드 그릴 때 순서
1. Client → (Command) → **Event Store(append-only)** 하나만 먼저 그린다. "여기가 유일한 진실."
2. Event Store → projection(읽기 모델) 화살표. "조회는 여기서."
3. 복원 화살표: snapshot + replay.
4. 그 다음에야 비동기(Outbox→Redis Stream), 팬아웃(Pub/Sub)을 얹는다.
> 순서가 중요하다. **진실의 원천을 먼저, 최적화는 나중에** 설명해야 "왜"가 산다.

### 답변 톤
- 결정마다 **"왜"와 "버린 대안"**을 같이 말한다. 면접관은 정답이 아니라 사고 과정을 본다.
- 모르는 건 "이건 측정해서 정해야 한다"고 정직하게. 추측을 단정하지 않는다.

## 1. 아키텍처 선택

### Q1-1. 왜 이벤트 소싱인가? 그냥 CRUD + 이력 테이블이면 안 되나?
**핵심 답변**: 과제의 1급 요구가 "임의 시점 t의 세션 상태 복원"입니다. CRUD는 현재 상태만 남기므로, 과거를 재구성하려면 별도 이력 테이블과 복원 로직을 *추가로* 붙이고, 그 이력과 현재 상태의 정합성을 *또* 관리해야 합니다. 이벤트 소싱은 이벤트가 유일 원천이라 — 복원은 그냥 이벤트를 다시 접는(fold) 것이고, 중복·순서·감사·읽기모델 재구축이 전부 같은 모델에서 파생됩니다. 즉 "복원"이 별도 기능이 아니라 모델의 자연스러운 성질이 됩니다.
**꼬리질문 대비**
- *"이벤트 소싱의 단점은?"* → 조회가 즉답이 안 됨(이벤트를 접어야 상태가 나옴), 스키마 진화가 까다로움(과거 이벤트 불변), 운영 복잡도↑. 그래서 CQRS(읽기 모델)와 스냅샷으로 조회를, upcasting으로 스키마 진화를 보완.
- *"오버엔지니어링 아닌가?"* → 복원이 부차 기능이면 그렇다. 하지만 이 과제는 복원이 명시적 1급 요구라 정당하다. 규모가 정말 작고 복원이 덜 중요하면 하이브리드(상태 테이블+이벤트 로그)로 단순화했을 것.

### Q1-2. CQRS를 왜 도입했고, 일관성은 어떻게 보장하나?
**핵심 답변**: 이벤트 소싱만 쓰면 조회 때마다 리플레이해야 해서 느립니다. 그래서 읽기 전용 projection 테이블(현재 참여자, 메시지 목록)을 별도로 두는 CQRS를 적용했습니다. 쓰기(이벤트 append)와 읽기(projection)를 분리하니 각각 독립적으로 최적화·확장됩니다. 대신 projection이 비동기라 **eventual consistency**입니다 — 방금 쓴 게 즉시 안 보일 수 있죠.
**꼬리질문 대비**
- *"방금 보낸 메시지가 안 보이면 UX 문제 아닌가?"* → ① 클라이언트가 자기 이벤트는 낙관적으로 즉시 표시(서버 확인 후 reconcile), ② projection lag을 모니터링해 SLA 관리, ③ 강한 일관성이 꼭 필요한 화면만 동기 projection 옵션. 전부 동기로 하면 CQRS 이점이 사라지므로 선택적으로.
- *"projection이 깨지면?"* → event store가 원천이므로 projection 테이블을 drop하고 리플레이로 재구축 가능. 이게 이벤트 소싱의 최대 강점.

## 2. 데이터 모델

### Q2-1. event payload를 JSONB로 한 이유는? 스키마 강제가 안 되는데?
**핵심 답변**: 이벤트 타입(메시지 송신/수정/삭제, join/leave, presence)이 이질적입니다. 타입별 컬럼으로 펼치면 희소(sparse) 컬럼이 폭증하고, 타입별 테이블로 나누면 append 경로가 복잡해집니다. JSONB로 로그를 균일하게 유지했습니다. payload 유효성은 **append 전 커맨드 경계에서 코드로 검증**하고, 이벤트는 write-once라 사후 변경이 없으니 DB 컬럼 제약의 이점이 작습니다. 결정적으로 **핫패스 쿼리가 payload 내부를 필터링하지 않습니다**(session_id + seq 범위로만 조회) — JSONB의 인덱싱 약점이 핫패스 비용으로 오지 않습니다.
**꼬리질문 대비**
- *"이벤트 스키마가 바뀌면 과거 이벤트는?"* → append-only라 과거 이벤트를 못 고친다. payload에 `version` 필드를 두고, 복원 fold 시 **upcasting**(구버전→신버전 변환)으로 처리. 이벤트 소싱의 표준 패턴.
- *"JSONB 대신 Avro/Protobuf는?"* → 직렬화 효율·스키마 레지스트리 이점이 있으나 PostgreSQL 단독 운영엔 JSONB가 디버깅·쿼리 편의가 큼. Kafka로 확장하면 그때 스키마 레지스트리 검토.

### Q2-2. seq(세션별 순서값)를 어떻게 원자적으로 채번하나? 동시성 문제는?
**핵심 답변**: `session` 행의 `last_seq`를 이벤트 append와 **같은 트랜잭션**에서 `UPDATE session SET last_seq = last_seq + 1 ... RETURNING`으로 증가시킵니다. 세션 단위로만 직렬화되고 세션 간은 완전 병렬입니다. 단일 세션 내 이벤트는 본래 저경합이라 비용이 무시할 만합니다.
**꼬리질문 대비**
- *"핫세션(초당 수천 메시지)이면 그 UPDATE가 병목 아닌가?"* → 맞다. 그 경우 seq 채번을 **Redis INCR**로 옮기되, DB의 `UNIQUE(session_id, seq)`를 **최종 권위/안전망**으로 유지. Redis는 성능, 진실은 DB 제약. 충돌 시 재채번/거부.
- *"DB 시퀀스(SERIAL)는 왜 안 쓰나?"* → 전역 시퀀스라 세션별 단조 증가를 보장 못 함. 세션마다 독립적인 순서가 필요해서 세션 스코프 카운터를 씀.

### Q2-3. 정규화/비정규화/JSONB 중 무엇을 택했고 왜?
**핵심 답변**: 혼합입니다. **쓰기 측(event)은 JSONB**로 유연하게, **읽기 측(projection)은 정규화된 테이블**로 조회 최적화. 이벤트 로그는 append 균일성이, 읽기 모델은 인덱스 효율이 중요해서 각 측의 목적에 맞췄습니다. CQRS라 한 모델에 두 요구를 욱여넣지 않아도 됩니다.

## 3. 중복 처리 (멱등성)

### Q3-1. at-least-once 환경에서 중복 이벤트를 어떻게 막나?
**핵심 답변**: **2계층 멱등성**입니다. ① **수집 시점** — `UNIQUE(session_id, idempotency_key)` 제약으로 클라이언트 재시도로 인한 중복 *유입*을 DB 레벨에서 차단(충돌 시 기존 이벤트 반환). ② **적용 시점** — projection worker가 `last_applied_seq` 가드로 Redis Stream의 at-least-once *재전달*을 차단. 두 계층은 **서로 다른 실패 지점**을 막기 때문에 둘 다 필요합니다.
**꼬리질문 대비**
- *"왜 한 계층으론 안 되나?"* → 수집 멱등성만으론 스트림 재전달(이미 저장된 이벤트의 중복 *적용*)을 못 막고, 적용 멱등성만으론 중복 seq 채번 자체를 못 막는다.
- *"idempotency_key는 누가 만들고 충돌하면?"* → 클라이언트가 논리적 액션당 UUID 부여(Stripe 등 결제 API의 표준 방식). 같은 키는 정의상 같은 액션 → 기존 결과 반환. 키 생성 책임을 클라에 두는 게 분산 환경의 정석.
- *"보존 기간은?"* → 무한 보존은 비현실적. 합리적 윈도우(예: 24~72h) 후 정리하되, 그 윈도우가 클라 재시도 최대 주기보다 길어야 함.

## 4. 순서 처리

### Q4-1. 순서가 뒤바뀐 이벤트의 "진짜 순서"를 어떻게 아나?
**핵심 답변**: 솔직히 — **모릅니다.** 그래서 "**서버 수신 순서 = 진실**"로 *정의*합니다. 분산 환경에서 클라이언트가 주장하는 순서(타임스탬프)는 시계 오차·조작 가능성으로 신뢰할 수 없습니다. 채팅 시스템의 표준 일관성 기준이 서버 도착 순서이고, 저는 이걸 **명시적 일관성 계약**으로 문서화했습니다. 서버가 append 시점에 채번한 seq가 유일한 순서 권위입니다.
**꼬리질문 대비**
- *"사용자가 A→B로 보냈는데 B가 먼저 도착하면 뒤집히지 않나?"* → 같은 클라이언트의 단일 커넥션(TCP/단일 WebSocket)이면 전송 순서가 보존된다. 서로 *다른* 클라이언트 간에는 애초에 전역 진실 순서가 존재하지 않음 — 서버 수신이 유일하게 정의 가능한 기준.
- *"벡터 클록이나 Lamport 타임스탬프는?"* → 인과관계가 비즈니스상 중요하면 고려. 하지만 채팅은 전역 전순서(total order)면 충분하고, 세션별 seq가 그걸 단순·확실하게 제공. 복잡도 대비 이득이 없어 배제.
- *"projection이 순서 어긋나게 받으면?"* → seq-guard: `seq == last+1`이면 적용, gap이면 event store에서 누락분을 fetch해 순서대로 적용, `seq <= last`면 skip. **스트림은 알림일 뿐 권위는 event store**라 항상 수렴.

## 5. 시점 복원

### Q5-1. 전체 리플레이 vs 스냅샷+리플레이, 무엇을 택했고 왜?
**핵심 답변**: **스냅샷 + 부분 리플레이**입니다. 전체 리플레이는 이벤트 수에 비례(O(n))해서 세션이 길어지면 복원 비용이 폭증합니다. 가장 가까운 스냅샷(up_to_seq ≤ at)을 로드하고 그 *이후* 이벤트만 접으면, **복원 비용 상한이 스냅샷 주기 N으로 고정**됩니다.
**꼬리질문 대비**
- *"스냅샷 주기 N은 어떻게 정하나?"* → 트레이드오프. N↑ = 스냅샷 저장·생성 비용↓, 복원 비용↑. N↓ = 반대. replay 행수를 메트릭으로 관측하면서 복원 SLA와 저장 비용의 균형점을 찾는다. POC 기본 200~500, 실측으로 조정.
- *"복원 중의 중복·순서는 어떻게 처리하나?"* (핵심 통찰) → **별도 처리 없음.** 복원은 이미 *정제된*(중복 제거·정렬된) 로그를 fold만 한다. 정제는 append 시점(멱등 제약 + seq 권위)에 1회 완료됨. 이게 이 모델의 우아함.
- *"at이 timestamp로 들어오면 seq 경계는?"* → `(session_id, occurred_at)` 인덱스로 `max(seq) where occurred_at <= at`을 구해 atSeq로 변환.
- *"스냅샷에 전체 메시지를 다 담나?"* → 아니오. "최근 N개"만(요구사항이 허용). 전체를 담으면 스냅샷 크기가 폭증. 더 과거가 필요하면 event에서 추가 리플레이.

## 6. 비동기 파이프라인

### Q6-1. 이벤트 DB 저장과 브로커 발행 중 하나만 성공하면? (dual-write)
**핵심 답변**: 전형적인 dual-write 문제입니다. **Transactional Outbox**로 해결했습니다 — event와 outbox 레코드를 *같은 트랜잭션*에 쓰고, 커밋된 후에 relay가 outbox를 읽어 Redis Stream에 발행합니다. DB 커밋이 곧 "발행 예약 확정"이라 이벤트 유실이 없습니다.
**꼬리질문 대비**
- *"relay가 발행하고 published 플래그 갱신 전에 죽으면 중복 발행?"* → 그렇다. at-least-once가 된다. 그래서 소비자(projection)를 멱등(seq-guard)하게 만들어 안전하다. "유실 방지 + 소비자 멱등"이 정석 조합.
- *"Outbox 폴링이 부담 아닌가?"* → `WHERE published = FALSE` 부분 인덱스로 미발행분만 스캔. 또는 LISTEN/NOTIFY로 푸시. 발행 완료분은 인덱스에서 빠져 스캔 비용이 일정.

### Q6-2. 재시도·DLQ는 어떻게 설계했나?
**핵심 답변**: Redis Stream consumer group의 ack/pending을 활용합니다. 처리 실패 시 XACK를 안 하면 pending에 남고, `XAUTOCLAIM`으로 idle timeout 후 재청구해 **지수 백오프**로 재시도합니다. 최대 횟수를 넘긴 독성 메시지는 `events:dlq` 스트림으로 격리하고 알람을 냅니다. event store가 원천이라 원인을 고친 뒤 언제든 재처리할 수 있습니다.

## 7. 실시간 / 수평 확장

### Q7-1. 인스턴스가 여러 대일 때 WebSocket 메시지를 어떻게 전달하나?
**핵심 답변**: 앱은 **stateless**이고 로컬 상태는 WebSocket 연결뿐입니다. 이벤트가 append되면 **Redis Pub/Sub** 채널 `session:{id}`로 발행하고, 모든 인스턴스가 구독하다가 자신에게 붙은 참여자에게 전달합니다(fan-out). 클라이언트가 어느 노드에 붙든 메시지를 받습니다.
**꼬리질문 대비**
- *"Redis가 SPOF 아닌가?"* → Sentinel/Cluster로 HA. 그리고 Redis는 *전송 계층*이라 죽어도 진실(PostgreSQL event store)은 무사. 복구 후 재발행으로 따라잡음.
- *"재연결 시 놓친 메시지는?"* → resume: 클라이언트가 마지막 `seq`를 들고 재접속하면 `event WHERE seq > lastSeq`만 재생해 정확히 따라잡음.

### Q7-2. 왜 Kafka가 아니라 Redis인가?
**핵심 답변**: POC 규모에서 Kafka는 운영 부담이 과합니다(주키퍼/KRaft, 파티션 관리, 로컬 구동 무게). Redis 하나로 Stream(파이프라인)+Pub/Sub(팬아웃)+presence(TTL)를 **3역할 단일 인프라**로 커버해 운영을 단순화했습니다. 다만 설계서에 **확장 경로로 Kafka를 명시**했습니다.
**꼬리질문 대비**
- *"그럼 언제 Kafka로 전환하나?"* → ① 처리량이 Redis Stream 한계를 넘을 때, ② 장기 보존·대규모 재처리가 필요할 때, ③ **파티션 키=session_id로 세션 샤딩**해 projection을 파티션별 스케일아웃해야 할 때. 세션 단위 파티셔닝이면 세션 내 순서가 파티션 내 순서로 보존돼 projection이 단순해짐.
- *"Redis Stream의 영속성은 Kafka보다 약한데?"* → 맞다. 그래서 Redis를 진실의 원천으로 삼지 않는다. event store가 원천이고 Redis 유실은 Outbox 재발행으로 복구 가능한 구조라 약한 영속성이 데이터 안전을 위협하지 않는다.

## 8. 장애 대응 (감지 → 완화 → 복구)

### Q8-1. 서버(인스턴스) 다운 시?
- **감지**: health check/heartbeat 누락. **완화**: LB가 트래픽 제거, 클라이언트 자동 재연결(타 인스턴스), presence TTL 만료로 자동 정리. **복구**: stateless라 재기동 즉시 합류, 죽은 인스턴스의 stream pending은 `XAUTOCLAIM`으로 타 인스턴스가 인계.

### Q8-2. DB 장애/성능 저하(커넥션 고갈·락 경합)?
- **감지**: 커넥션풀 포화율, 쿼리 p99, 락 대기 메트릭. **완화**: append 우선순위 보장, 읽기는 스냅샷/캐시로 degrade, 풀 상한+statement timeout, seq 채번이 세션 단위 락이라 경합이 세션 국소로 한정. **복구**: read replica로 조회 분산, 백프레셔로 유입 조절.

### Q8-3. 데이터 유실/정합성(중복 저장·부분 실패)?
- **감지**: projection lag 급증, DLQ 증가, 스냅샷↔이벤트 정합성 배치 체크. **완화**: Outbox로 유실 방지, 멱등 키로 중복 저장 차단. **복구**: **event store가 원천이라 read model을 언제든 리플레이로 재구축**. projection 전체를 drop하고 다시 만들 수 있음 — 이벤트 소싱 최대 강점.

## 9. 관측성 / 성능

### Q9-1. 무엇을 모니터링하나? 핵심 SLI는?
**핵심 답변**: **projection lag**(이벤트 발생~읽기모델 반영 지연)과 **DLQ size**가 핵심 SLI입니다. 이 둘이 임계 초과면 읽기 모델이 뒤처지거나 독성 메시지가 쌓이는 것 — 가장 먼저 알아야 할 신호죠. 그 외 append rate/latency, stream pending, snapshot age, restore latency·replay 행수를 봅니다. 로그는 session_id/seq/event_id/trace_id 상관키로 구조화하고 OpenTelemetry로 append→relay→projection을 추적합니다.

### Q9-2. 핫패스 쿼리와 병목·개선은?
**핵심 답변**: 3개입니다. ① **이벤트 append+중복체크** — unique 제약 2개로 처리, 병목은 핫세션의 last_seq UPDATE 직렬화 → Redis INCR로 개선. ② **최근 N개 메시지** — `(session_id, seq DESC)` 인덱스, 병목은 `state<>'DELETED'` 후필터 → partial index. ③ **시점 복원** — 스냅샷 부재 구간이 길면 replay 폭증 → 스냅샷 주기 보장 + replay 행수 알람.

## 10. 메타 / 트레이드오프 질문 (까다로운 것)

### Q10-1. 이 설계의 가장 큰 약점은?
**핵심 답변**: **복잡도**입니다. 이벤트 소싱+CQRS+비동기 파이프라인은 단순 CRUD보다 학습·운영·디버깅 부담이 큽니다. eventual consistency로 인한 UX 고려도 필요하죠. 그래서 **Phase로 핵심(동기 동작)부터 완성**하고 비동기·확장을 점진 적층하도록, 그리고 강한 일관성이 필요한 부분은 동기 옵션을 두도록 설계했습니다. 복잡도를 *인지하고 통제*하는 게 중요하다고 봅니다.

### Q10-2. 다시 설계한다면 무엇을 바꾸겠나?
**핵심 답변**: 규모와 복원 중요도에 달렸습니다. 만약 복원이 부차 기능이고 트래픽이 작다면 **하이브리드(상태 테이블 + 이벤트 로그)**로 단순화했을 겁니다. 하지만 이 과제는 복원이 1급 요구라 풀 이벤트 소싱이 정당합니다. 즉 "정답"이 아니라 **요구에 맞춘 선택**이라는 점을 강조하고 싶습니다.

### Q10-3. 구현 못한/생략한 부분은?
**핵심 답변**: 정직하게 — 이벤트 스키마 버저닝(upcasting)은 설계만 하고 구현은 미정, 스냅샷 주기 N의 최적값은 실측 튜닝 필요, presence 하트비트 간격·멱등 키 보존기간은 운영 파라미터로 남겼습니다(설계서 §14 미해결 항목). 측정 없이 단정하지 않는다는 원칙입니다.

### Q10-4. 메시지가 수억 건 쌓이면?
**핵심 답변**: ① event 테이블을 session_id 또는 시간 기준 **파티셔닝**(오래된 세션 콜드 스토리지로). ② Kafka 전환 + 파티션 샤딩. ③ 스냅샷 주기 단축으로 복원 비용 유지. ④ 종료된(ENDED) 세션은 최종 스냅샷만 남기고 이벤트 아카이빙. 핵심은 **event store가 원천이라 콜드/핫 분리가 자유롭다**는 것.
